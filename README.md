# BookRoom — бронирование переговорных

Тестовое задание для стажёра Frontend Avito, осенняя волна 2026.

BookRoom — веб-приложение, в котором сотрудник может выбрать офис, найти свободную переговорную на нужный интервал, посмотреть расписание комнаты, создать бронирование и управлять своими будущими встречами.

Авторизация замокана предоставленным backend. Backend остаётся источником истины и повторно проверяет временные ограничения и конфликты бронирований.

## Реализовано

- список переговорных с обязательным выбором офиса;
- фильтры по дате, времени, продолжительности и вместимости;
- отображение доступности комнат на выбранный интервал;
- страница комнаты с информацией и расписанием на день;
- создание бронирования с клиентской и серверной валидацией;
- обработка конфликта бронирования `409 BOOKING_CONFLICT`;
- просмотр предстоящих и прошедших бронирований пользователя;
- фильтрация бронирований по офису и периоду;
- отмена собственного будущего бронирования;
- loading, error и empty-состояния;
- страница 404 для неизвестных маршрутов;
- WebSocket-обновления списка комнат и открытого расписания;
- переподключение WebSocket с повторной синхронизацией данных и индикатором состояния соединения;
- unit-тесты компонентов, API-функций и вспомогательной логики.

## Технологии

- **React 19** — пользовательский интерфейс;
- **TypeScript** — типизация данных и компонентов;
- **Vite** — dev-сервер и production-сборка;
- **react-router-dom** — маршрутизация;
- **Material UI** — компоненты интерфейса и тема приложения;
- **TanStack Query** — загрузка, кеширование и повторное получение серверных данных;
- **date-fns и @date-fns/tz** — работа с датами и часовыми поясами офисов;
- **WebSocket** — real-time обновления;
- **Vitest и Testing Library** — unit-тесты;
- **ESLint и Prettier** — проверка качества и форматирование кода.

## Требования

- Node.js 20 или новее;
- npm;
- свободные порты `3000` для backend и `5173` для frontend.

## Установка

После клонирования репозитория установите зависимости отдельно для backend и frontend:

```bash
npm ci --prefix server
npm ci --prefix frontend
```

Создайте файл окружения frontend из примера:

```bash
cp frontend/.env.example frontend/.env
```

Backend запускается со значениями по умолчанию. Его переменные окружения из `server/.env.example` можно экспортировать средствами оболочки, если требуется изменить конфигурацию.

## Запуск приложения

Из корня проекта выполните:

```bash
npm run dev
```

Команда одновременно запускает backend и frontend и корректно останавливает оба процесса по `Ctrl+C`.

После запуска доступны:

- frontend — <http://localhost:5173>;
- backend — <http://localhost:3000>;
- документация API — <http://localhost:3000/documentation>;
- WebSocket — `ws://localhost:5173/api/v1/ws` через Vite proxy.

При необходимости приложения можно запустить отдельно:

```bash
npm run dev:server
npm run dev:frontend
```

Эти команды запускаются из корня проекта в разных терминалах.

## Архитектура frontend

Код разделён по назначению:

```text
frontend/src/
├── app/       # провайдеры, тема и общий layout
├── entities/  # модели и API офисов, комнат, пользователей и бронирований
├── pages/     # страницы и относящиеся к ним UI-компоненты
├── shared/    # API-инфраструктура, конфигурация, real-time и общий UI
└── test/      # общая настройка и фикстуры тестов
```

Компоненты страниц отвечают за сборку интерфейса и состояние экрана. Работа с REST API вынесена в `entities/*/api`. Серверные данные хранятся в кеше TanStack Query, поэтому не дублируются в отдельном глобальном хранилище.

После WebSocket-событий клиент инвалидирует связанные query keys. TanStack Query повторно запрашивает актуальные данные через REST, поэтому backend продолжает быть источником истины. После восстановления соединения инвалидируется весь кеш — это компенсирует отсутствие журнала пропущенных событий на сервере.

## Принятые решения

### Выбор офиса

До выбора офиса запрос списка комнат не выполняется, а фильтры времени недоступны. Это соответствует требованию об обязательном офисе для отображения переговорных.

### Даты и часовые пояса

Интервалы отправляются в API в ISO 8601. Локальное время рассчитывается с учётом `timezone`, полученного для выбранного офиса. Даты ограничены текущим днём и 30 днями вперёд, время — рабочим интервалом с 09:00 до 20:00, а начало и продолжительность имеют шаг 15 минут.

### Фильтр периода бронирований

Backend поддерживает `scope=upcoming|past|all`, но не принимает произвольный диапазон дат. Поэтому вкладки загружают предстоящие или прошедшие бронирования через API, а варианты «Сегодня», «За 7 дней» и «За 30 дней» дополнительно фильтруются на клиенте.

### Работа с API в development

Frontend использует относительный адрес `/api/v1`. Vite proxy перенаправляет HTTP- и WebSocket-запросы на backend по адресу `http://localhost:3000`.

Во время разработки прямой `DELETE`-запрос с frontend на backend блокировался браузером на этапе CORS preflight. Same-origin proxy устранил проблему без изменения предоставленного backend и одновременно сделал конфигурацию REST и WebSocket единообразной.

### Единый запуск

В корне добавлен скрипт `scripts/dev.mjs`. Он запускает обе части проекта одной командой и завершает второй процесс, если frontend или backend остановился с ошибкой.

## Ограничения

Не реализованы необязательные дополнительные задания:

- оптимистическая отмена с rollback;
- экспорт бронирования в `.ics`;
- повторяющиеся бронирования.

Production-сборка может показывать предупреждение Vite о размере основного JavaScript-бандла. Оно не влияет на работоспособность приложения; дальнейшая оптимизация возможна через lazy loading маршрутов и разделение кода.
